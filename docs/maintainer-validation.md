## Automation design

- Toolkit `v0.9.3` was confirmed as the latest stable release and its tag resolved.
- `Step 0` has a real `push` start event and a manual recovery event. Its first-run
  guard refuses to replace an existing exercise, including a closed one.
- The toolkit start workflow disables all numbered workflows before this
  repository enables `Step 1`. Unnumbered `Check report` stays available.
- All three `Check report` jobs skip template repositories. This prevents maintenance PRs in the publishing repository from being graded as learner submissions, while retaining report, evidence, and reproduction checks in learner copies. Keep the workflow enabled; the job guards distinguish the two contexts.
- Step 1 and step 2 validate specification pushes to `main`.
- Their job guards skip branch-creation pushes, including a learner copy's
  initial push. All workflows start enabled in a new copy until Step 0 disables
  the later lessons; without this guard, Steps 1 and 2 can look for the exercise
  issue before Step 0 creates it. Later edits and manual recovery remain enabled.
- Step 3 checks same-repository implementation PR artifacts from exact head SHAs.
- Step 4 runs on pushes to `main` affecting implementation files, reports, or review evidence. It skips branch creation and resolves the merged PR whose merge commit equals the pushed commit. This avoids an additional Copilot PR workflow-approval gate for completion without weakening PR checks. It checks merged artifacts/evidence, posts the recap, then invokes the toolkit to update the README and close the exercise issue.
- Completion also requires the unprivileged reproduction check to have passed
  on the merged PR's exact head commit. Manual recovery requires the PR number
  that produced current `main`; it cannot replace the merge requirement.
- The baseline checker is checked out from the PR base for Step 3 and from the pre-push `main` commit for automatic Step 4, separately from candidate data. Manual recovery uses current `main`. Grading jobs have no contents/actions write and execute no learner Python. Their issue-write token is used only for feedback; final grading also has read access to pull requests and checks.
- Unprivileged `Check report` jobs validate artifacts/evidence and reproduce the
  reports/run tests separately. The reproduction checker uses fresh temporary
  directories without report files, compares newly generated bytes, requires a
  nonempty runnable test suite, and checks the three invalid-input fixtures.
  Candidate execution has no write token, no persisted checkout credentials, and
  no explicitly supplied secrets.
- No `pull_request_target`, privileged artifact execution, package installation,
  live data connection, or deployment is used.
- Shared local actions handle feedback and transitions. Feedback lookup is scoped
  to the bot and the stable `## Step N -` results heading; it cannot select a
  learner's own comment.

Structural prose grading cannot prove semantic quality. Declared evidence cannot prove
the analyst actually read the sources. The learner must inspect the PR, understand
the rule explanations, and verify the source-derived examples. Source, specification,
and checker changes are rejected in implementation PRs; legitimate specification
revisions must be deliberate changes on `main` before requesting implementation.

## Simplified implementation and review requests

Step 3 now asks the learner to describe the outcome, follow the specification, preserve the source data, and retain human approval. Technical requirements live in `.github/copilot-instructions.md`, which GitHub Copilot coding agent reads automatically. It directs the agent to the existing data dictionary and implementation reference and preserves the required Python paths, standard-library constraint, test and verification commands, generated reports, and protected-file boundaries.

Step 4 likewise uses a plain-language request to check the reports, correct errors in the existing pull request, and explain unresolved issues. The repository instructions require the agent to rerun generation, tests, and independent verification, regenerate corrected reports, and leave the analyst's review decision and merge untouched.

The grading and reproduction workflow wiring is unchanged. The analyst still completes `verification/review-evidence.md`; the coding agent must not write that evidence or merge the pull request. Local regression and structure checks can verify compatibility, but automatic instruction loading and the shorter request still need a live learner-copy run.

## Checklist-based analyst review

Step 4 now records four checked review items and `Decision: approved` instead of repeating customer figures, totals, transaction IDs, and a rationale. The learner compares the reports with their step-2 calculations, marks each completed item `[x]`, resolves discrepancies, and approves on the implementation PR's branch.

The evidence grader rejects unchecked, missing, renamed, duplicate, or malformed required items and missing, duplicate, or pending decisions. Report values are still independently recomputed from unchanged sources before evidence is checked, and reproduction and merged-PR completion requirements remain intact. A checked checklist is a declaration, not proof of human authorship or actual inspection.

## Pull request totals summary

Copilot includes known-customer, unmatched-customer, and independently calculated September source totals in a table in the PR description. The analyst compares that summary with the specification's Expected results rather than manually adding the generated rows again. The CSV formats remain unchanged.

Generated artifacts, Analyst evidence, and Steps 3 and 4 validate the summary against independently derived source totals. Pull request checks and Step 3 also handle `edited` events so description-only corrections rerun grading. Normal PR checks read the event payload without an API token. Step 4 reads the merged PR description using its grading token with `pull-requests: read`: automatic completion resolves the PR from the pushed merge commit, and manual recovery uses the selected PR number. The existing merged-PR and successful reproduction requirements still apply.

## Final-step workflow approval regression

The live exercise exposed two separate interruptions: GitHub requested maintainer approval for the Copilot PR's final `pull_request` workflow, then the grading job could not read the PR because its token lacked `pull-requests: read`. The template now starts completion from the human-approved merge's push to `main` and explicitly grants that read permission. It does not use `pull_request_target`, auto-approve Copilot workflows, or execute the submitted implementation in a write-capable job.

Regression checks cover exact merge-commit association, missing or ambiguous merged PRs, foreign repositories and wrong base branches, incomplete analyst approval, incorrect PR-description totals, and failed or missing reproduction checks. Structural validation requires the main-push trigger, initial-copy guard, scoped paths, and PR-read permission. A fresh learner-copy run must still verify that merging starts completion without another approval prompt; earlier PR checks may still require GitHub's normal approval.
